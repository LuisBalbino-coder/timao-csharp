Trilha web e back-end

A maior fatia do mercado de C#: APIs, sistemas e serviços com ASP.NET Core. Três módulos para você sair de um endpoint "olá" até um CRUD com banco e autenticação.

  1. Minimal API — seu primeiro endpoint

W1

Minimal API — seu primeiro endpoint

MapGet · MapPost · rota · injeção de dependência · JSON automático

Uma API é um programa que responde requisições HTTP com dados (quase sempre JSON). No ASP.NET Core moderno, o formato Minimal API cria endpoints em poucas linhas — e o framework já serializa objetos para JSON, valida rotas e trata erros.

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// lista em memória só para o exemplo
var elenco = new List<Jogador>
{
    new(1, "Rodrigo Garro", 10, 12),
    new(2, "Yuri Alberto", 9, 17)
};

// GET /jogadores
app.MapGet("/jogadores", () => elenco);

// GET /jogadores/1 — 404 se não existir
app.MapGet("/jogadores/{id:int}", (int id) =>
{
    var j = elenco.FirstOrDefault(x => x.Id == id);
    return j is null ? Results.NotFound() : Results.Ok(j);
});

// POST /jogadores — recebe JSON no corpo e devolve 201
app.MapPost("/jogadores", (Jogador novo) =>
{
    elenco.Add(novo);
    return Results.Created($"/jogadores/{novo.Id}", novo);
});

// DELETE /jogadores/1
app.MapDelete("/jogadores/{id:int}", (int id) =>
    elenco.RemoveAll(j => j.Id == id) > 0
        ? Results.NoContent()
        : Results.NotFound());

app.Run();

public record Jogador(int Id, string Nome, int Camisa, int Gols);
  • MapGet, MapPost, MapPut, MapDelete definem rotas por verbo HTTP.
  • {id:int} é route constraint: a rota só casa se for inteiro.
  • Parâmetros simples vêm da rota/query; objetos complexos vêm do corpo JSON automaticamente.
  • Results.Ok, NotFound, Created, NoContent devolvem os status HTTP corretos (200, 404, 201, 204).
  • O middleware embutido cuida de CORS, logging, compressão e tratamento de erro — você configura em builder.Services.

W2

EF Core e banco de dados

DbContext · DbSet · migrations · LINQ no banco

EF Core é o ORM oficial do .NET: você escreve classes C# e ele cuida do SQL. Cada DbContext representa uma sessão com o banco e cada DbSet<T> é uma tabela.

using Microsoft.EntityFrameworkCore;

public class Jogador
{
    public int Id { get; set; }
    public string Nome { get; set; } = "";
    public int Camisa { get; set; }
    public int Gols { get; set; }
}

public class TimaoContext : DbContext
{
    public DbSet<Jogador> Jogadores => Set<Jogador>();

    protected override void OnConfiguring(DbContextOptionsBuilder o) =>
        o.UseSqlite("Data Source=timao.db");
}

// ---------- instalar e migrar ----------
// dotnet add package Microsoft.EntityFrameworkCore.Sqlite
// dotnet add package Microsoft.EntityFrameworkCore.Design
// dotnet tool install --global dotnet-ef
// dotnet ef migrations add Inicial && dotnet ef database update

using var db = new TimaoContext();

// criar
db.Jogadores.Add(new Jogador { Nome = "Garro", Camisa = 10, Gols = 12 });
db.SaveChanges();                       // aqui o INSERT acontece

// consultar (LINQ vira SQL, não carrega a tabela toda)
var artilheiros = db.Jogadores
    .Where(j => j.Gols >= 10)
    .OrderByDescending(j => j.Gols)
    .ToList();

// atualizar
var garro = db.Jogadores.FirstOrDefault(j => j.Camisa == 10);
if (garro is not null)
{
    garro.Gols += 1;
    db.SaveChanges();
}

// remover
db.Jogadores.Where(j => j.Gols == 0).ExecuteDelete();
  • DbContext é descartável: use using ou injeção de dependência (escopo por requisição).
  • Migrations versionam o esquema do banco a partir das suas classes.
  • SaveChanges agrupa tudo numa transação: ou salva tudo, ou nada.
  • Use AsNoTracking() em leitura pura: economiza memória e é mais rápido.
  • Evite consultar dentro de laço (problema N+1): use Include ou uma consulta só.

W3

Autenticação, configuração e deploy

JWT · secrets · Docker · produção

API pronta é API protegida, configurada e publicada. Os três assuntos que separam "funciona na minha máquina" de "está no ar".

// ---------- 1. Configuração e segredos ----------
// appsettings.json  →  { "Jwt": { "Chave": "..." } }
// NUNCA coloque segredo no código nem no repositório:
//   dotnet user-secrets init
//   dotnet user-secrets set "Jwt:Chave" "valor-super-secreto"
var chave = builder.Configuration["Jwt:Chave"];

// ---------- 2. Autenticação JWT (resumo) ----------
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization();

app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/perfil", (ClaimsPrincipal user) =>
    $"Olá, {user.Identity?.Name}")   // vem do token
   .RequireAuthorization();

// ---------- 3. Erros sem vazar detalhes ----------
app.UseExceptionHandler(erro => erro.Run(async ctx =>
{
    ctx.Response.StatusCode = 500;
    await ctx.Response.WriteAsJsonAsync(new { erro = "Erro interno" });
}));

// ---------- 4. Injeção de dependência ----------
builder.Services.AddSingleton<IRepositorioJogadores, RepositorioEmMemoria>();
builder.Services.AddScoped<TimaoContext>();   // uma por requisição

app.MapGet("/jogadores", (IRepositorioJogadores repo) => repo.Todos());
  • JWT é um token assinado: o servidor confia nele sem consultar o banco a cada requisição.
  • Segredos vão em user-secrets (dev) ou variáveis de ambiente (produção) — nunca no Git.
  • Ciclos de vida na DI: Singleton (um para o app), Scoped (um por requisição), Transient (novo a cada uso).
  • Em produção: HTTPS obrigatório, UseExceptionHandler, logs estruturados e limite de requisições.
  • Deploy comum: publicar com dotnet publish -c Release, rodar atrás de Nginx, ou empacotar em Docker (mcr.microsoft.com/dotnet/aspnet).
